The Roots Behind Every Answer

Every answer our assistant gives starts underground, in an index of 2.1 million chunks. Here is how we pick the three that matter, and how we check that we picked right.

  1. Chunk by structure, not by token count We split documents on headings, tables, and code blocks. A table cut in half answers nothing, so tables stay whole. Median chunk: 280 tokens.
  2. Two searches, one list Dense embedding search and keyword search run in parallel, merged with reciprocal rank fusion. Embeddings catch meaning; keywords catch part numbers and error codes the embeddings blur.
  3. A re-ranker that pays for its 90 ms A cross-encoder re-scores the top 50 candidates. On our internal benchmark it lifts the right passage into the top three from 81% of questions to 93%.
  4. Cite it or skip it The model can only quote retrieved passages, and every claim links to its chunk. When nothing clears the relevance bar, the assistant says it doesn’t know.

What we still get wrong: questions that need eight documents instead of three.

12,000 Questions Before a Model Ships

No model reaches customers until it has answered our full eval suite. What is in it, how we grade it, and why the 588 failures teach us more than the 11,412 passes.

  1. Three shelves of 4,000 Reasoning, code, and safety. Every question carries a reference answer and a rubric, written by the engineer who owns that area.
  2. Graders we check every week Exact match where we can, unit tests for code, a model grader for open answers. We compare the model grader against 300 human-graded samples each week. If they disagree more than 5% of the time, we rewrite the grader and leave the threshold alone.
  3. Regressions block, averages don’t A new model can score higher overall and still not ship. Any question that passed last release and fails now goes to a person before launch.
  4. The suite grows from bug reports Every customer bug becomes a new question within a week. That added 1,900 questions this year.

Next up: publishing the safety shelf so customers can run it themselves.

Reading a Loss Curve From the Summit Down

A training run is 40,000 steps of one number going down. We walk the curve from the first steep drop to the long flat stretch and say what each shape told us.

  1. The cliff, steps 0 to 4K Loss falls fast while the model learns the easy structure. It looks dramatic and tells you little. Almost any sane config gets this far.
  2. The spike at 16K One data shard full of duplicated boilerplate. Loss jumped for 300 steps. We now deduplicate shards by hash before they enter the mix, and skip any batch whose gradient norm is 4× the running median.
  3. The long flat, 20K to 40K Progress drops to fractions of a percent. This is where the learning-rate schedule earns its keep: cosine decay bought another 3% on held-out loss.
  4. Where the lines part At 29K the validation loss starts climbing while training loss keeps falling. We ship the checkpoint from where they separate, not the last one.

41 Steps to Fix One Bug

We gave our coding agent a real ticket from the backlog and logged every move. Here is the full trace: 41 tool calls, one wrong turn, one green test suite.

  1. Steps 1 to 9: read before touching Grep for the error string, read four files, read the failing test. A fifth of the run went to reading, and it is the part we would least want to cut.
  2. Steps 10 to 23: the wrong fix It patched the symptom in the request handler. The tests ran and failed on an edge case in a file it hadn’t opened.
  3. Steps 24 to 38: the retry Instead of stacking a second patch, it reverted and traced the bad value back to the parser. The failing test output was the most useful thing in its context.
  4. Steps 39 to 41: done means green Full suite passes. It writes a pull request that explains the fix and the dead end. Six minutes, 212K tokens.

The full trace is published alongside this post, one line per step.
